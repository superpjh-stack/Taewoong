## 1. 개요

### 배경

사이드바 재구조화(sidebar-restructure) Plan에서 검사출하관리(`/shipments`)가 최상위 메뉴로 확정되었고, 품질검사(`/quality`)가 그 하위로 편입되었다. 사업계획서 p.42는 검사출하관리 하위에 5개 기능을 정의한다. 현재 구현된 것은 품질검사(`/quality`) 페이지뿐이며, 나머지 4개 하위메뉴는 미구현 상태다.

### 목적

- 출하 LOT 라이프사이클 전체(입고 → 공정 → 검사 → 출하)를 단일 모듈에서 추적·관리한다.
- Heat No. 기준 Traceability를 고객 대응 및 품질 감사에 즉시 활용할 수 있도록 한다.
- AI Agent를 통해 출하 적합성 자동 판단 및 납기 리스크 조기 경보를 제공한다.

### 범위

| 항목 | 포함 여부 |
|------|-----------|
| 출하관리 CRUD (`/shipments/management`) | 포함 |
| 출하이력조회 (`/shipments/history`) | 포함 |
| 출하 데이터관리 CRUD (`/shipments/data`) | 포함 |
| 품질검사 CRUD (`/quality`) — 기존 페이지 이동 | 포함 |
| 출하 AI Agent 조회 (`/shipments/ai-agent`) | 포함 |
| AI 판단 모델 훈련·재학습 파이프라인 | 제외 (AI 서비스 팀 별도 계획) |
| 고객사 포털 연동(EDI, B2B API) | 제외 |

## 2. 하위메뉴별 사용자 스토리

### 2-1. 출하관리

**AS-IS**: 출하 LOT 등록·수정·삭제가 엑셀 수작업으로 이루어져 납기 스케줄과 실제 출하 상태 간 불일치가 빈번하다.

| ID | 사용자 스토리 | 완료 조건 |
|----|------------|---------|
| US-01 | 출하 담당자로서 출하 LOT를 등록하고 고객사·납기일을 설정하여 납기 스케줄을 통합 관리하고 싶다. | 출하 LOT 등록 후 목록에 즉시 반영되고, 납기일 기준 정렬이 동작한다. |
| US-02 | 출하 담당자로서 기존 출하 건의 상태(준비/출하중/완료)를 수정하여 진행 현황을 갱신하고 싶다. | 상태 변경 시 변경 이력이 audit_log에 기록된다. |
| US-03 | 관리자로서 출하 LOT를 삭제(소프트 딜리트)하여 오등록 건을 처리하고 싶다. | 삭제된 건은 목록에서 숨겨지나 이력 조회에서는 확인 가능하다. |

### 2-2. 출하이력조회

**AS-IS**: 제품별 출하 이력과 검사 결과가 분리된 시스템에 저장되어 고객 클레임 대응 시 데이터 취합에 수 시간이 소요된다.

| ID | 사용자 스토리 | 완료 조건 |
|----|------------|---------|
| US-04 | 품질 담당자로서 Heat No.를 입력하여 해당 제품의 전체 출하 이력과 검사 결과를 한 화면에서 조회하고 싶다. | Heat No. 검색 결과가 1초 이내 반환된다. |
| US-05 | 품질 담당자로서 특정 고객사·기간 조건으로 출하 이력을 필터링하여 클레임 대응 자료를 추출하고 싶다. | 필터 적용 후 결과를 CSV로 내보낼 수 있다. |
| US-06 | 경영진으로서 월별 출하 현황을 집계 뷰로 확인하여 납기 이행률을 파악하고 싶다. | 월별 납기 이행률(%) 집계 지표가 화면에 표시된다. |

### 2-3. 출하 데이터관리

**AS-IS**: 출하 데이터와 검사 데이터가 각기 다른 담당자에 의해 관리되어 정합성 오류가 발생한다.

| ID | 사용자 스토리 | 완료 조건 |
|----|------------|---------|
| US-07 | 데이터 관리자로서 출하 데이터와 검사 데이터를 통합 뷰에서 조회하여 정합성을 점검하고 싶다. | 두 도메인 데이터의 불일치 항목이 하이라이트된다. |
| US-08 | 데이터 관리자로서 누락된 검사 데이터를 수동 입력하여 KPI 산출 기반을 완성하고 싶다. | 수동 입력 데이터에 입력자·입력일시가 자동 태깅된다. |
| US-09 | 시스템 관리자로서 출하 데이터를 정기 백업하고 이상 데이터를 아카이빙하여 시스템 무결성을 유지하고 싶다. | 백업 작업 결과가 로그로 기록된다. |

### 2-4. 품질검사

**AS-IS**: `/quality` 페이지가 독립 최상위 메뉴로 존재하여 검사-출하 흐름이 시각적으로 단절되어 있다.

| ID | 사용자 스토리 | 완료 조건 |
|----|------------|---------|
| US-10 | 검사 담당자로서 LOT별 검사 항목(치수, 경도, 성분)을 입력하고 합격/불합격을 판정하고 싶다. | 검사 결과 저장 시 해당 LOT의 상태가 자동 갱신된다. |
| US-11 | 검사 담당자로서 불합격 판정 건에 사유와 조치 내용을 기록하여 품질 추적성을 확보하고 싶다. | 불합격 사유가 quality_inspections 테이블에 저장된다. |
| US-12 | 품질 담당자로서 검사 항목별 합격률 추이를 확인하여 공정 품질 개선 포인트를 발굴하고 싶다. | 최근 30일 합격률 트렌드 차트가 표시된다. |

### 2-5. 출하 AI Agent

**AS-IS**: 출하 적합성 판단이 검사 담당자의 경험에 의존하여 판단 기준의 일관성이 낮다.

| ID | 사용자 스토리 | 완료 조건 |
|----|------------|---------|
| US-13 | 출하 담당자로서 AI가 검사 결과와 공정 데이터를 종합하여 출하 적합성을 자동 판단한 결과를 확인하고 싶다. | AI 판단 결과에 신뢰도 점수(0~100)와 판단 근거가 함께 표시된다. |
| US-14 | 출하 담당자로서 납기 리스크 지수를 실시간으로 확인하여 지연 예상 건에 선제 대응하고 싶다. | 납기 리스크 지수 산출 공식: `(잔여 작업량 / 일평균 처리량) / 잔여 납기일`. 위험 임계값 초과 시 알림 표시. |
| US-15 | 관리자로서 AI 판단 결과를 수동으로 재검토·승인하여 최종 출하 결정 권한을 유지하고 싶다. | AI 판단 결과에 대해 "승인/반려" 액션이 제공되며, 결과가 audit_log에 기록된다. |

## 4. API 엔드포인트 목록

| 메서드 | 경로 | 기능 | 하위메뉴 |
|--------|------|------|---------|
| GET | `/shipments` | 출하 목록 조회 (페이징, 필터) | 출하관리 |
| POST | `/shipments` | 출하 LOT 등록 | 출하관리 |
| PATCH | `/shipments/:id` | 출하 정보 수정 | 출하관리 |
| DELETE | `/shipments/:id` | 출하 소프트 딜리트 | 출하관리 |
| GET | `/shipments/history` | 출하이력 목록 (필터, 페이징) | 출하이력조회 |
| GET | `/shipments/history/:heatNo` | Heat No. 기준 출하이력 + 검사결과 | 출하이력조회 |
| GET | `/shipments/history/export` | 출하이력 CSV 내보내기 | 출하이력조회 |
| GET | `/shipments/data` | 출하+검사 통합 데이터 조회 | 출하 데이터관리 |
| POST | `/shipments/data` | 누락 데이터 수동 입력 | 출하 데이터관리 |
| PATCH | `/shipments/data/:id` | 데이터 수정 | 출하 데이터관리 |
| GET | `/quality-inspections` | 검사 목록 조회 | 품질검사 |
| POST | `/quality-inspections` | 검사 결과 등록 | 품질검사 |
| PATCH | `/quality-inspections/:id` | 검사 결과 수정 | 품질검사 |
| GET | `/quality-inspections/trend` | 합격률 30일 트렌드 | 품질검사 |
| GET | `/shipments/:id/ai-assessment` | 출하 적합성 AI 판단 결과 조회 | 출하 AI Agent |
| GET | `/shipments/delivery-risk` | 납기 리스크 지수 목록 조회 | 출하 AI Agent |
| POST | `/shipments/:id/ai-assessment/approve` | AI 판단 결과 승인/반려 | 출하 AI Agent |

> 모든 엔드포인트는 kebab-case 복수형 경로 규칙을 따른다.
> AI 판단 결과 응답 스키마에는 반드시 `confidence_score` 필드가 포함되어야 한다.

## 5. 구현 우선순위

### 이터레이션 1 (Must Have — 핵심 CRUD)

| 순서 | 작업 | 대상 하위메뉴 |
|------|------|-------------|
| 1 | `shipments` 테이블 스키마 확인 및 마이그레이션 | 출하관리 |
| 2 | 출하관리 CRUD API 구현 | 출하관리 |
| 3 | 품질검사 API 기존 코드 이관 (`/quality` → `/shipments` 하위 서브메뉴 연결) | 품질검사 |
| 4 | Heat No. 기준 출하이력 조회 API 구현 (Traceability) | 출하이력조회 |

### 이터레이션 2 (Should Have — 분석 및 AI 연동)

| 순서 | 작업 | 대상 하위메뉴 |
|------|------|-------------|
| 5 | 납기 리스크 지수 계산 로직 구현 | 출하 AI Agent |
| 6 | 출하 AI Agent API 연동 (AI 서비스 인터페이스 정의) | 출하 AI Agent |
| 7 | 합격률 트렌드, 납기 이행률 집계 API 구현 | 출하이력조회, 품질검사 |
| 8 | 출하 데이터관리 통합 뷰 및 수동 입력 API | 출하 데이터관리 |

### 이터레이션 3 (Could Have)

- 데이터 정합성 자동 검증 배치
- AI 판단 결과 승인/반려 워크플로우
- CSV 내보내기

### 완료 기준 (Acceptance Criteria)

- [ ] 5개 하위메뉴 라우트(`/shipments/management`, `/shipments/history`, `/shipments/data`, `/quality`, `/shipments/ai-agent`)가 사이드바에서 접근 가능
- [ ] 출하 LOT 등록·수정·삭제(소프트 딜리트) 정상 동작
- [ ] Heat No. 입력 시 1초 이내 출하이력 + 검사결과 통합 조회
- [ ] AI 판단 결과 응답에 `confidence_score` 필드 포함
- [ ] 납기 리스크 지수 공식 기반 계산값 UI에 표시
- [ ] 모든 데이터 변경이 audit_log에 기록
